2. Forma de trabajo#

  • Gestión: un GitHub Issue por tarea (IDs de este documento en el título, p. ej. [N-12] Endpoint Top N), agrupados en un Milestone por fase y un Project board (Backlog → In progress → Review → Done).
  • Ramas: trunk-based con ramas cortas feat/…, fix/…, docs/…, test/…; PR obligatorio a main con CI verde (desde Febrero, branch protection).
  • Commits: Conventional Commits (feat(scores): submit score endpoint).
  • Definition of Done por tarea: código + tests relevantes + Swagger actualizado + sin warnings + documentación afectada actualizada.
  • Estimación: tamaños S (≤ 2 h), M (≤ ½ día), L (≤ 1 día). Ninguna tarea L sin dividir si supera 1 día.

4. Fase 1 · Noviembre — Base funcional + Swagger#

Objetivo: flujo completo usable desde Swagger contra PostgreSQL local. Estructura: un único proyecto Leaderboard.Api con carpetas Domain/, Application/, Infrastructure/, Endpoints/ (prepara el refactor de Enero).

4.1 Scaffolding y fundamentos#

  • N-01 (S) global.json fijando SDK .NET 10 LTS; solución Leaderboard.sln; .gitignore, .editorconfig
  • N-02 (S) Directory.Build.props (Nullable, ImplicitUsings, TreatWarningsAsErrors, AnalysisLevel=latest-recommended) y Directory.Packages.props (gestión central de versiones)
  • N-03 (S) Proyecto Leaderboard.Api (Minimal APIs) con carpetas por capa
  • N-04 (S) compose.yaml mínimo solo con PostgreSQL para desarrollo local (la API corre con dotnet run)
  • N-05 (M) OpenAPI (Microsoft.AspNetCore.OpenApi) + Swagger UI en /swagger (solo Development) con esquema Bearer
  • N-06 (M) ProblemDetails global: AddProblemDetails + IExceptionHandler + traceId + code
  • N-07 (M) Tipos base: Result<T>, Error, ErrorType y extensión Result → IResult
  • N-08 (S) PagedResult<T> + PageRequest con validación (page ≥ 1, 1 ≤ pageSize ≤ 100)
  • N-09 (S) FluentValidation + filtro de endpoint ValidationFilter<T> → ValidationProblemDetails

4.2 Dominio y persistencia#

  • N-10 (M) Entidades de dominio: Player, Game (con ScoreOrder, ScoreRange), GameApiKey, Score, LeaderboardEntry + tests de invariantes básicos
  • N-11 (M) AppDbContext + IEntityTypeConfiguration<T> por entidad (snake_case con EFCore.NamingConventions, citext, xmin)
  • N-12 (M) Migración inicial InitialCreate con índices de la sección 3.3 de arquitectura
  • N-13 (S) Aplicar migraciones al arrancar si Database:MigrateOnStartup=true
  • N-14 (S) Seed opcional de datos de demo (juego + 50 jugadores) en Development — parcial: solo el administrador (Seed:Admin); los datos masivos están en perf/seed.sql

4.3 Autenticación (RF-01, RF-02, RF-05, RF-06)#

  • N-15 (M) POST /auth/register con PasswordHasher<Player>, unicidad email/username → 409
  • N-16 (M) JwtTokenService (HS256, 15 min, claims sub, unique_name, role, jti) + opciones validadas al arrancar (ValidateOnStart)
  • N-17 (S) POST /auth/login con error genérico auth.invalid_credentials
  • N-18 (S) GET /players/me
  • N-19 (S) Swagger: botón Authorize funcional con Bearer

4.4 Juegos y API Keys (RF-10…RF-15)#

  • N-20 (M) POST /games, GET /games (paginado + search), GET /games/{id}
  • N-21 (M) Política GameOwner (autorización por recurso, 404 si no es propietario)
  • N-22 (S) PATCH /games/{id} y DELETE /games/{id} (archivar)
  • N-23 (M) Emisión de API Key: keyId (lbk_ + 16 chars), secreto 256 bits (RandomNumberGenerator), cifrado con Data Protection; secreto devuelto una sola vez
  • N-24 (S) Listar y revocar API Keys
  • N-25 (M) ApiKeyAuthenticationHandler modo simple (X-Api-Key: keyId.secret, FixedTimeEquals) + política GameServer

4.5 Scores y Leaderboard (RF-20…RF-27)#

  • N-26 (L) POST /games/{id}/scores: validación de rango, juego activo, jugador existente; transacción con INSERT score + upsert ON CONFLICT de leaderboard_entries
  • N-27 (M) Respuesta con isPersonalBest, bestScore, rank, totalPlayers
  • N-28 (M) LeaderboardReadService: Top N y ranking paginado con rank_key normalizado y desempate
  • N-29 (M) Posición absoluta (rango + percentil)
  • N-30 (M) Ventana relativa (around?range=k) con dos consultas keyset
  • N-31 (S) Ejemplos y descripciones OpenAPI en todos los endpoints (WithSummary, Produces<ProblemDetails>)

4.6 Cierre de fase#

  • N-32 (S) Colección .http (Leaderboard.Api.http) con el flujo completo de demo — sustituido por Swagger UI con firma en el navegador y samples/submit-score.sh
  • N-33 (S) README: sección «Cómo ejecutar» (versión provisional con dotnet run)
  • N-34 (S) Tag v0.1.0 + nota de release — pendiente: etiquetar al fusionar en main

✅ Criterio de salida: desde Swagger se completa registro → login → crear juego → emitir clave → enviar 3 scores (con la clave) → Top N y posición correctos.

5. Fase 2 · Diciembre — Tests + documentación extensa#

Objetivo: red de seguridad antes del refactor de Enero (los tests de integración son el contrato que el refactor no puede romper).

5.1 Infraestructura de tests#

  • D-01 (S) Proyectos Leaderboard.UnitTests y Leaderboard.IntegrationTests (xUnit v3, Shouldly, NSubstitute, coverlet)
  • D-02 (M) ApiFactory : WebApplicationFactory<Program>, IAsyncLifetime con Testcontainers PostgreSQL (un contenedor por colección)
  • D-03 (M) Respawn para limpiar la BD entre tests; builders de datos (PlayerBuilder, GameBuilder) y helpers AuthenticateAsAsync(...), CreateApiKeyAsync(...)
  • D-04 (S) FakeTimeProvider registrado en tests para controlar tiempo (expiración de tokens, desempates)

5.2 Tests unitarios#

  • D-05 (M) Dominio: Game.IsBetter(a, b), ScoreRange, RankKey para ambos ScoreOrder, invariantes de Player/Game
  • D-06 (M) Validadores FluentValidation (casos límite de username, password, paginación, n, range)
  • D-07 (M) Handlers de aplicación con repositorios falsos (registro duplicado, juego archivado, fuera de rango)
  • D-08 (S) JwtTokenService (claims, expiración) y generación/verificación de API Keys

5.3 Tests de integración (una clase por feature)#

  • D-09 (M) Auth: registro, duplicados, login OK/KO, /players/me con y sin token
  • D-10 (M) Games: CRUD, BOLA (otro usuario → 404), archivado
  • D-11 (M) API Keys: emisión (secreto solo una vez), listado sin secreto, revocación → 401
  • D-12 (L) Scores: récord personal, score peor, fuera de rango, juego archivado, clave de otro juego (403)
  • D-13 (L) Leaderboard: Top N con empates, LowerIsBetter, paginación, bordes de la ventana relativa, percentil
  • D-14 (M) Concurrencia: 50 envíos paralelos del mismo jugador → una sola entrada con el máximo correcto (RNF-07)
  • D-15 (S) Contrato de errores: todas las respuestas 4xx/5xx son application/problem+json con traceId y code
  • D-16 (S) El documento OpenAPI se genera sin errores (GET /openapi/v1.json → 200)

5.4 Funcionalidad y documentación#

  • D-17 (M) Refresh tokens con rotación y detección de reutilización (RF-03) + POST /auth/logout (RF-04)
  • D-18 (S) GET /leaderboard/me y GET /players/me/scores (RF-28)
  • D-19 (M) README extenso: arquitectura, decisiones, ejemplos curl, cómo ejecutar tests, badges
  • D-20 (S) Informe de cobertura (ReportGenerator) y umbral objetivo documentado
  • D-21 (S) Tag v0.2.0 — pendiente: etiquetar al fusionar en main

✅ Criterio de salida: dotnet test verde en local; cobertura Domain+Application ≥ 70 % (objetivo final 80 %).

6. Fase 3 · Enero — Clean Architecture + ADRs#

Objetivo: separar en 4 proyectos sin cambiar el comportamiento externo (los tests de integración de Diciembre son el árbitro).

6.1 Refactor#

  • E-01 (M) Crear Leaderboard.Domain y mover entidades/VOs/errores (sin dependencias NuGet)
  • E-02 (L) Crear Leaderboard.Application: mover handlers, DTOs, validadores; definir puertos (IPlayerRepository, IGameRepository, IScoreRepository, IUnitOfWork, ILeaderboardReadService, ITokenService, ICurrentUser)
  • E-03 (M) Abstracciones CQRS liviano (ICommand<T>, ICommandHandler<,>, IQuery<T>, IQueryHandler<,>) + registro por assembly scanning (Scrutor) + decoradores de validación y logging
  • E-04 (L) Crear Leaderboard.Infrastructure: AppDbContext, configuraciones, migraciones, repositorios, read services, seguridad; AddInfrastructure(IConfiguration)
  • E-05 (M) Adelgazar Leaderboard.Api: solo endpoints, auth handlers, error handling, composición
  • E-06 (M) Separar tests: Domain.UnitTests, Application.UnitTests, Api.IntegrationTests
  • E-07 (M) Leaderboard.ArchitectureTests con NetArchTest: Domain sin dependencias; Application no referencia Infrastructure/EF/AspNetCore; handlers sealed; endpoints no referencian DbContext

6.2 Anti-cheat (primera parte)#

  • E-08 (L) ApiKeyHmacAuthenticationHandler: cadena canónica, ventana ±300 s, FixedTimeEquals; flag ApiKeys:AllowPlainSecret
  • E-09 (M) Idempotencia por UNIQUE(api_key_id, nonce): reintento → 200 con resultado original (RF-29)
  • E-10 (S) Límite de 5 claves activas por juego (RF-16)
  • E-11 (S) Script/cliente de ejemplo (samples/sign-request.ps1 y .sh) que firma peticiones para probar desde terminal — parcial: samples/submit-score.sh (bash); falta la variante PowerShell
  • E-12 (M) Tests de integración HMAC: firma alterada, cuerpo alterado, timestamp caducado, replay, clave revocada

6.3 ADRs#

  • E-13 (M) docs/adr/0001-postgresql.md — PostgreSQL vs SQL Server vs MongoDB vs Redis-first
  • E-14 (M) docs/adr/0002-clean-architecture.md — Clean vs Vertical Slice vs N-capas; coste/beneficio del refactor
  • E-15 (M) docs/adr/0003-anti-cheat.md — API Key simple vs HMAC vs JWT de servidor vs mTLS; rate limiting; plausibilidad
  • E-16 (S) Actualizar docs/architecture.md si alguna decisión cambió; regenerar HTML
  • E-17 (S) Tag v0.3.0 — pendiente: etiquetar al fusionar en main

✅ Criterio de salida: 4 proyectos, tests de arquitectura verdes, todos los tests de Diciembre verdes sin modificar sus aserciones, 3 ADR publicados.

10. Riesgos y mitigaciones#

# Riesgo Prob. Impacto Mitigación
R1 El refactor de Enero rompe comportamiento Media Alto Tests de integración de Diciembre como red; refactor en PRs pequeños por capa.
R2 Testcontainers lento o inestable en CI Baja Medio Un contenedor por colección + Respawn; imagen postgres:18-alpine cacheada.
R3 Sobre-ingeniería (CQRS, specs) para un proyecto pequeño Media Medio CQRS «liviano» sin bus; ADR-002 explicita el trade-off y dónde no se aplica.
R4 Consultas de ranking lentas con muchos datos Baja Alto rank_key + índice cubriente; benchmark M-17 (el riesgo se materializó y se corrigió: ver performance.md); plan B Redis documentado.
R5 Filtración de secretos (JWT key, API Keys) Baja Alto user-secrets / .env no versionado, secret scanning, cifrado Data Protection.
R6 Retraso por disponibilidad personal (festivos de Diciembre) Alta Medio Diciembre con menor carga funcional; tareas S/M paralelizables; buffer en la última semana de cada mes.
R7 Cambios de licencia en librerías (.NET OSS) Media Bajo Preferir librerías de Microsoft o licencias MIT/Apache estables; decisiones registradas en arquitectura §7.1.
